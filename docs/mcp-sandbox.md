# Песочница для MCP-серверов — план

Продолжение [mcp-apps.md](mcp-apps.md). Там разобрано, как six показывает приложение и чем оно ограничено; здесь
— то, что осталось за скобками: **процесс**, который six запускает по stdio, и что он может сделать с машиной.

Коротко о положении дел. Приложение (HTML) уже в клетке: два origin, CSP из заголовка, `isPlausibleSource`,
разрешения через `SitePermissions`, ворота на `tools/call`. Запуск процесса — нет: `MCPServerProcess` не
пропускает команду через оболочку и не запускает ничего по своей инициативе, но то, что запущено, получает **полные
права пользователя и весь env логин-шелла**. Это ровно то место, где стоят и Claude Desktop, и Claude Code: диалог
на вызов инструмента есть, песочницы для процесса нет. Агентные браузеры эту задачу не решают, потому что не
запускают локальных процессов вовсе. Зато у браузера есть то, чего нет у настольного клиента: веб-процесс, в
котором целый Node или CPython уже умеют жить целиком — см. уровень 4.

## Модель угроз

Три действующих лица, и у каждого свой рычаг.

| кто | чем опасен | что уже есть |
|---|---|---|
| **процесс сервера** — чужой код с правами пользователя | файлы, сеть, env с токенами, другие процессы, персистентность | нет оболочки; `--mcp-probe` и обход не запускают пакеты; `mcpApps.shared` пуст по умолчанию |
| **подмененная конфигурация** — запись в `six.sqlite`, в сохранённом `MCPAppCatalog.json`, пакет из реестра | six сам запустит что скажут | плейсхолдеры выбрасываются; `Add` из поиска не пробует пакет |
| **агент под инъекцией** — страница уговорила модель вызвать инструмент | вызов чужого инструмента с чужими аргументами | делиться сервером — отдельное решение; для приложений — `MCPAppBar` |

Что защищаем, в порядке цены:

1. **Файлы пользователя.** Всё, что не нужно серверу для работы.
2. **Токены в окружении.** `LoginShell.environment()` — это `zsh -l -i -c env` целиком: `GITHUB_TOKEN`, `AWS_*`,
   `OPENAI_API_KEY`, всё, что человек когда-то экспортировал в `.zshrc`.
3. **Сетевое положение.** Процесс на машине видит `localhost`: базы, dev-серверы — и **сокет самого six**
   (`Application Support/org.deffun.six/mcp.sock`). Любой процесс пользователя может к нему подключиться и водить
   браузер через его же инструменты. Сервер, который так делает, не нуждается ни в какой инъекции.
4. **Остальные процессы и службы.** AppleScript, XPC, Keychain-запросы от имени пользователя.

Чего **не** защищаем и не обещаем: сервер, честно работающий с разрешённым хостом, может отправить туда что
угодно из того, что ему дали; сервер может врать в результатах инструмента — это уже вопрос агента, не
песочницы.

## Словарь: что серверу нужно на самом деле

Песочница без словаря — это либо «запрещено всё» (и тогда не работает `npx`), либо «разрешено всё» (и тогда
зачем). Смысл stdio-сервера — локальный доступ, значит, нужна **декларация**, и её нет в стандарте: ни MCP, ни
реестр, ни ext-apps не описывают, что серверу можно. У реестра есть `environmentVariables` и `packageArguments`,
у ext-apps — `ui.csp` для *приложения*. Для процесса — ничего. Значит, словарь свой, маленький:

```swift
struct MCPServerGrants: Codable {
    /// Куда можно ходить по сети. Пусто — никуда.
    var hosts: [String]            // "api.example.com", "*.example.com"
    /// Что можно читать и писать сверх собственной папки.
    var paths: [Path]              // { path, write: Bool }
    /// Какие переменные окружения отдать по имени.
    var environment: [String]
}
```

Умолчания по происхождению сервера — это и есть политика:

| откуда сервер | `hosts` | `paths` | `environment` |
|---|---|---|---|
| пакет из реестра (`npx`, `uvx`) | `remotes` записи + реестры пакетов | ничего | ничего |
| вписан руками (`command`) | спрашиваем при добавлении | спрашиваем | спрашиваем |
| удалённый (URL) | — не процесс — | — | — |

То же самое хорошо ложится на карточку подтверждения: человек видит **командную строку, источник и три списка**
и говорит «да» один раз на эту командную строку. Это «manifest-only execution model», который CSA рекомендует как
замену сырому stdio-конфигу, только у нас манифест пишет хост, а не сервер.

## Четыре уровня

Каждый — отдельно поставляемый шаг; каждый следующий не отменяет предыдущего, а стоит на нём. Первый — дни; четвёртый —
два коротких эксперимента, и он идёт вторым; второй и третий — для того, что в веб-процесс не помещается.

### Уровень 1. Договор — дни

Ничего не изолирует, но закрывает половину модели угроз ценой пары сотен строк.

- **Карточка перед первым запуском.** Как «Run Again» у восстановленного окна: `shellCommandLine` целиком,
  источник (реестровый namespace / «by hand» / каталог), гранты. Помнится по командной строке, не по имени:
  изменилась строка — спрашиваем снова. Закрывает и «`Add` из поиска не показал, что запустит», и подмененную
  запись каталога.
- **Белый список окружения.** `PATH`, `HOME`, `LANG`/`LC_*`, `TMPDIR`, `TERM`, `SSL_CERT_*` плюс
  `definition.environment` плюс `grants.environment`. Всё остальное из `LoginShell.environment()` не отдаётся.
  `SIX_MCP_SOCKET` — в частности.
- **Свой `HOME`.** `AppSupport/servers/<id>/` как `HOME`, `XDG_*` и `TMPDIR`. Кэш `npx` и `uv` ложится туда, а
  не в `~`, и удаляется вместе с сервером. Без песочницы это соглашение, а не запрет — но `npm`, `uv`, `pip`
  соглашение соблюдают.
- **`command` только из доверенных мест.** Сохранённый `MCPAppCatalog.json` в Application Support перекрывает
  встроенный по `generated` и сегодня может принести запись с командой. Не должен: команда — только из бандла и из
  `mcpApps.servers`, куда пишет сам six после карточки.

Где: `MCPServerDefinition` (+`grants`), `MCPServerProcess` (env), `MCPAppStore.open` (карточка), `MCPCatalog.current`.

### Уровень 2. Seatbelt — недели

Настоящая клетка, без виртуальной машины и без потерь в скорости, и ровно та, которую Anthropic поставляет для
Claude Code: [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) генерирует Seatbelt-профиль
на macOS и bubblewrap-контейнер на Linux, сеть пускает только на localhost-порты своих прокси, и в README прямо
называет «local MCP servers» одним из назначений. Это TypeScript и `sandbox-exec`; нам нужен тот же **чертёж** на
Swift.

`sandbox-exec` формально deprecated, но на macOS 27 на месте и работает (проверено). Мы им не пользуемся всё
равно: **маленький лаунчер** в бандле, `six-launch`, который делает `sandbox_init(profile)` и `execve` — то же,
что делают Chromium и WebKit для своих helper-процессов. Дети наследуют профиль, так что `npx → node → sh` остаётся
внутри.

Профиль (SBPL) собирается из грантов на каждый запуск:

```scheme
(version 1)
(deny default)
(allow process-exec process-fork)                      ; npx запускает node
(allow file-read* (subpath "/usr") (subpath "/System") (subpath "/Library/Frameworks")
                  (subpath "<node>") (subpath "<uv>"))  ; резолвлено из PATH, не весь $HOME
(allow file-read* file-write* (subpath "<AppSupport>/servers/<id>"))
(allow file-read* (subpath "<grants.paths[read]>"))
(allow file-read* file-write* (subpath "<grants.paths[write]>"))
(allow network-outbound (remote ip "localhost:<proxy>"))  ; и больше никуда
(deny network-inbound)
(deny mach-lookup)                                      ; ни AppleScript, ни XPC к чужим приложениям
(allow sysctl-read)                                     ; node без этого не стартует
```

**Сеть — через прокси.** Seatbelt умеет «разрешить/запретить», но не «только на api.example.com». Поэтому: six
поднимает локальный HTTP `CONNECT`-прокси (у него уже есть `MCPLoopback` — тот же кусок), пускает только
`grants.hosts`, а серверу отдаёт `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`. Node 24+ понимает их с
`NODE_USE_ENV_PROXY=1`, Python — из коробки. Сервер, который env-прокси игнорирует, сети не имеет вовсе — закрыто
по умолчанию, и это правильная сторона ошибки. Заодно **`localhost` для сервера исчезает** — и сокет six вместе с
ним.

**Linux** — то же самое через `bubblewrap`: `--unshare-net`, bind-mount тех же папок, сеть через тот же прокси
по `--share-net` с фильтром. Один словарь, два бэкенда, как у sandbox-runtime.

Что ломается и как узнаем: сервер, которому нужен `~/.ssh` или Keychain, падает с `EPERM` в stderr —
`MCPServerProcess` его уже собирает, карточка покажет «сервер просил X, запрещено» и предложит добавить грант.
Это лучше, чем молча дать.

Где: новая цель `six-launch` (C или Swift, ~80 строк), `MCPSandboxProfile` (SBPL из грантов), `MCPEgressProxy`,
`MCPServerProcess` (запуск через лаунчер).

### Уровень 3. Виртуальная машина — по выбору, недели

[apple/containerization](https://github.com/apple/containerization) — Swift-пакет, не только CLI: каждый
контейнер — своя лёгкая ВМ на Virtualization.framework, старт менее секунды, RPC для запуска процесса с потоками
stdin/stdout, virtiofs для общих папок, у каждого контейнера свой IP. Требует macOS 26 — six уже требует. Это
**та самая «контейнер вокруг каждого сервера» рекомендация индустрии**, но нативная и встраиваемая.

Что даёт сверх Seatbelt: изоляция от ядра macOS и от всех его служб — Keychain, AppleScript, TCC, всё остаётся
снаружи по построению, а не по профилю. Гостевой Linux, значит, `npx` и `uvx` живут в образе `six-runtime`
(node + uv + git), а не в `~/.nvm` пользователя.

Что стоит, честно:

- **Память.** Одна ВМ — сотни мегабайт; на 8 ГБ машине два-три сервера в контейнерах — уже вопрос. Поэтому не
  «всё в ВМ», а **переключатель на сервере**: пакет из реестра по умолчанию в контейнер, вписанный руками — как
  скажут.
- **Ядро и образ.** Фреймворку нужно ядро Linux (`make fetch-default-kernel` тянет kata-ядро) и rootfs. Это
  загрузка при первом использовании, десятки мегабайт, и это надо где-то хранить и обновлять.
- **Только Linux внутри.** Сервер, которому нужен macOS — AppleScript, локальные приложения, Photos — в
  контейнер не поедет. Для него остаётся уровень 2.
- **Файлы** — только virtiofs-шары, то есть `grants.paths` в точности; больше ничего гость не видит.
- **Только Apple silicon и macOS 26+.** На Linux-фронте — bubblewrap из уровня 2, на iOS — ничего.

Транспорт не меняется: `MCPStdioTransport` получает stdin/stdout из RPC фреймворка вместо `Pipe`, всё выше не
знает разницы. Прокси из уровня 2 стоит на хосте, ВМ ходит в него по своему IP.

Где: `MCPContainerProcess` рядом с `MCPServerProcess`, зависимость `Containerization` в проекте (не в `SixCore`),
образ `six-runtime` и место под ядро в Application Support.

### Уровень 4. Сервер внутри веб-процесса — то, что может только браузер

Сначала поправка к тому, что было написано в первой редакции: «wasm не изолирует существующие серверы» —
неверно. Класс WebContainers ровно это и делает: **целый Node с настоящим `npm`, или CPython с пакетами,
исполняется внутри вкладки браузера**, в wasm и воркерах, без единого процесса снаружи. Это существует, это
открыто, и это работает в WebKit. А six — браузер. Так что для него это не «ещё один рантайм», а **тот же
механизм, которым уже показано приложение**, повёрнутый на сервер:

| | приложение (уже есть) | сервер (этот уровень) |
|---|---|---|
| где живёт | веб-процесс WebKit, свой origin | веб-процесс WebKit, свой origin |
| stdio | `postMessage` через `MCPAppBridge` | тот же `postMessage`, третий транспорт `MCPWebTransport` |
| файлы | нет | виртуальная ФС в IndexedDB/OPFS — **пользовательских файлов нет по построению** |
| сеть | `connect-src` из `ui.csp` | `connect-src` из `grants.hosts` — **egress по хостам без прокси**, тем же `isPlausibleSource` |
| сверху | песочница веб-процесса | она же |
| iOS | да | **да** — WKWebView имеет JIT, wasm и воркеры; это единственный уровень, который туда доезжает |

Чем исполнять — искал прежде, чем предлагать писать своё:

| рантайм | лицензия | что внутри | npm / pip | WebKit |
|---|---|---|---|---|
| [vivari](https://github.com/maitrungduc1410/vivari) | MIT | **настоящий `lib/` Node** на JS-движке браузера, ядро-VFS на Rust/wasm, синхронный I/O через `Atomics.wait` в воркере; `child_process`, `net`, `http` | настоящие `npm`/`yarn`/`pnpm` с lock-файлом и кэшем | не заявлен — но примитивы есть, см. ниже |
| [NodePod](https://github.com/ScelarOrg/NodePod) | MIT + Commons Clause | 40+ полифиллов, своя оболочка, 600 КБ | `npm install` | evergreen |
| [BrowserPod](https://github.com/leaningtech/browserpod-meta) | проприетарный, бесплатно для personal/OSS | **бинарник Node 22, собранный в wasm**, на своём syscall-ядре; Python — preview | npm, bash | заявлен Safari |
| [WebContainers](https://webcontainers.io/) | коммерческий | свой | npm | Safari — beta, нужен `credentialless` COEP |
| [Pyodide](https://pyodide.org/) | MPL-2.0 | CPython 3.14 в wasm, 356 собранных пакетов | micropip для чистых колёс с PyPI | да |
| [WasmKit](https://github.com/swiftwasm/WasmKit) | Apache | для серверов, собранных под WASI; в процессе six, без веб-вида | — | — |

Для Python проверено по `pyodide-lock.json` 314.0.6: всё, что нужно `mcp`-SDK и собирается из C/Rust, уже там —
`pydantic-core`, `anyio`, `httpx`, `httpcore`, `starlette`, `jsonschema`, `cryptography`, `sqlalchemy`, `numpy`,
`pandas`. Остальное (`mcp`, `sse-starlette`, `python-multipart`, `pydantic-settings`) — чистый Python, ставится
micropip'ом. Pydantic закрыли свой `mcp-run-python` со словами «no safe way to run Python within pyodide safely with
reasonable latency» — их случай был «чужой код на каждый запрос за миллисекунды»; наш — долгоживущий сервер, которому
секунды на старт не мешают.

**Что установлено спайком, и от чего зависит всё остальное.** Классу WebContainers нужен `SharedArrayBuffer`, а
WebKit выдаёт его только кросс-origin-изолированной странице. Проверено на macOS 27 ([Tests/Spikes/CrossOriginIsolation.swift](../Tests/Spikes/CrossOriginIsolation.swift)):

| страница отдана | `crossOriginIsolated` | `SharedArrayBuffer` | `Atomics.wait` в воркере | `Atomics.waitAsync` |
|---|---|---|---|---|
| `six-spike://` через `WKURLSchemeHandler`, с COOP/COEP | **true** | **нет** — `ReferenceError` | — | есть |
| `http://127.0.0.1` с COOP/COEP | true | **есть** | **блокирует** (вернул `timed-out` через 50 мс) | есть |

То есть изоляция по своей схеме *считается*, но JS-глобал её не получает, и публичного переключателя нет — в
списке фич WebKit только `CrossOriginOpenerPolicyEnabled`/`CrossOriginEmbedderPolicyEnabled`, уже включённые.
Вывод простой: **страницу-хост сервера отдаёт loopback**, не custom scheme. У six уже есть `MCPLoopback` — тот же
кусок, только с COOP/COEP и `Cross-Origin-Resource-Policy` на всём, что страница грузит; всё это six отдаёт сам.
Побочный факт для приложений: окно на `mcp-app-content://` SAB тоже не получит, и это нормально.

Чего этот уровень не умеет, и это граница, а не недоработка:

- **Нативные аддоны (`.node`) — нет** ни в одном рантайме; сервер на `better-sqlite3` или `sharp` идёт на уровни 2–3.
  Но `@modelcontextprotocol/sdk` и подавляющее большинство серверов реестра — чистый TypeScript.
- **Настоящие файлы и бинарники** (`git`, `ffmpeg`) — нет; это и есть песочница. `grants.paths` здесь пуст,
  обмен файлами — явный импорт/экспорт через six.
- **Python с C-расширениями** — только из набора Pyodide.
- **Память** — веб-процесс на сервер, десятки–сотни мегабайт; но six и так держит процесс на окно, и это всё
  равно дешевле ВМ.
- **Старт** — Pyodide грузится секунды в первый раз, потом из кэша; vivari заявляет миллисекунды.

**Эксперимент, два раза по два дня.** Первый: `server-basic-vanillajs` (чистый JS) внутри vivari внутри скрытой
страницы six по loopback — `MCPWebTransport` вместо `Pipe`, всё выше не меняется. Второй: Python-сервер на
Pyodide с `mcp` через micropip. На выходе — да/нет по каждому и цифры памяти и старта. Если vivari в WebKit не
заведётся на `Atomics.wait` — примитивы есть, значит, это их баг, и его стоит починить им, а не обходить нам.

## Что это значит для интерфейса

Один значок на строке сервера в `six://apps` и в заголовке окна-приложения — уровень доверия, в котором сервер
живёт:

| значок | что за ним |
|---|---|
| `network` | удалённый сервер — процесса нет |
| `terminal` | процесс, уровень 1: договор, но без стен |
| `lock.shield` | процесс за Seatbelt (уровень 2) |
| `cube` | в контейнере (уровень 3) |
| `globe` | в веб-процессе six (уровень 4) — и на iOS |
| `cpu` | WASI-модуль в процессе six (WasmKit) |

И одна карточка при первом запуске, общая для всех уровней: командная строка, источник, гранты, где будет жить.

## Порядок

1. **Уровень 1** сразу — он дешёвый, и без него уровни 2–4 не с чем показывать человеку.
2. **Уровень 4** вторым, а не последним — это переоценка после спайка. Он переиспользует всё уже построенное
   для окон, покрывает большинство серверов реестра (чистый TS и Python), даёт egress по хостам без прокси и
   единственный доезжает до iOS. Два эксперимента по два дня дают ответ раньше, чем Seatbelt дойдёт до профиля.
3. **Уровень 2** для того, что в веб-процесс не помещается: нативные аддоны, настоящие файлы, `git`. Чертёж
   sandbox-runtime, авторы серверов под ним уже живут.
4. **Уровень 3** — переключатель для остального, когда памяти хватает.

Что не делаем: не пишем свою виртуализацию, не тащим Docker, не ждём стандарта — его нет и не предвидится, а
словарь из трёх списков переживёт любой, который появится.
